1. 一句话结论

War3 用的是经典 确定性锁步（deterministic lockstep）：所有客户端不各自推进模拟，而是把本玩家的输入打包成“回合（Turn）”里的命令，经 NetRouter 发给所有对端；每一回合只有当所有玩家该回合的命令块（TurnsSyncChunk）都到齐，各端才用完全相同的输入 + 相同的随机种子推进同一回合的模拟。模拟结束后各子系统分别算校验和并交换比对，不一致就触发可信 desync 事件。

3. 核心机制拆解

3.1 命令是网络对象：CNetCommand 族

玩家的一切操作（移动、攻击、施法、聊天 ping、方向键，甚至作弊码）都被做成 CNetCommandBase 的子类对象，随回合一起同步。RTTI 里可见的族系：

类含义
CNetCommandBase网络命令基类
CNetCommandAllyPing / CNetCommandArrowKey盟友 ping、方向键输入
CNetCommandCheatBase 及其 20+ 子类作弊也是命令：God、Gold、Lumber、FastBuild、ShowMap、Victory/Defeat、TechTree……（所以作弊也要参与同步与校验，见 §3.4 的 cheat checksum）
CAbility*Command（如 CAbilityAuraCommand）技能命令

关键点：命令先同步、后执行。本地输入不会立刻生效，而是先进入本回合的 ClientTurn，等所有人到齐后才统一执行——这就是锁步消除“先看到先动手”的做法。

FUN_6f3098d0 是个按事件类型（0x01–0x31）的大 switch：Connect、Disconnect、GameList、GameCreate、GameJoin、PlayerJoin/Leave/Ready、GameSetup、GameStart、GameReady、Trigger……每个 case 生成对应的 CNetEvent* 对象交给上层。它还负责两件事：

  • 录像：GameStart（0x1b）时写 TempReplay.w3g；每条网络命令还可写 NET_COMMAND_SAVE 记录——录像文件本质就是“回合命令流”的回放。
  • 逐玩家状态表：以 0x304 为步长索引玩家槽（+0x278 字段为每玩家状态计数器），分发前先核对玩家状态。

3.5 路由与锁步模式

  • FUN_6f283540 引用字符串 Router is running in lockstep mode——路由器明确工作在锁步模式下。
  • CNetEventSetTurnsLatency（事件 0x21）：回合延迟是可调参数，用来吸收网络抖动——等一等、攒够了再推进，是锁步对抗延迟的标准做法。
  • CNetEventRouterHandoff*（0x26–0x2a）：主机交接事件，主机掉线时把路由职责移交，保证回合流不断。
  • CNetEventDistFile*（0x2b–0x2d）：地图文件分发，保证所有人用同一张图开局——同步的前提是同一份初始状态。

5. 确定性从哪里来（设计要点）

  • 同一输入：所有操作先变成命令、随回合同步，人人拿到同一份命令表。
  • 同一随机数：随机数子系统单独校验（rand checksum）——随机数发生器是确定性种子序列，不是各机器自己掷骰子。
  • 同一初始状态：地图分发（DistFile）+ 同一版本校验，保证开局状态一致。
  • 同一节奏：回合是推进单位，不是墙钟时间；SetTurnsLatency 只调等待，不调模拟步长。
  • 可验证：七子系统校验和 + 网络事件流校验和 + 迷雾校验和，三层交叉验证；一旦不一致就以 TrustedDesync 事件定性，而不是静默跑偏。
学习价值：这套设计对任何实时多人模拟都通用——“命令进回合、回合等人齐、模拟要确定、状态可校验、跑偏要定性”。实现时最关键的其实是最后一点：War3 不追求“绝不 desync”，而是追求“desync 一定能被发现、定位到子系统、并以事件形式上报”。
未验证 / 待深挖：回合的 wall-clock 节奏（每秒几回合）未从本次反编译中确认；七子系统校验和的具体哈希函数与 CTurnsSyncStore 的“等齐”超时/丢包重传逻辑未展开；FUN_6f3098d0 的 0x15/0x1b 预处理分支只读了主干。以上可作为下一步定向深挖点。
